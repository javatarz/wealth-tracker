# Testing strategy: four seam layers plus property-based tests for financial maths

## Test seams

| Layer | What it tests | How |
|-------|--------------|-----|
| **Parser** | casparser extracts the right data from a CAMS CAS PDF | Fixture PDF (`tests/fixtures/mock_cams_cas.pdf`) fed through casparser; expected output hand-verified and stored as golden JSON |
| **Financial maths** | XIRR, lot-reduction (FIFO), time-weighted return | Pre-computed answers from a spreadsheet (or known-good library) stored as test expectations. Every run compares against these golden values |
| **API contract** | Endpoints accept and return the right shapes | OpenAPI spec-driven — generated TypeScript types on the frontend side, Pydantic-validated on the backend. Contract tests use `openapi-core` to verify request/response against the spec |
| **Frontend** | Components render correctly, user flows work | Vitest + React Testing Library for component tests; Playwright for a small set of critical-path E2E tests (import flow, dashboard load) |

## Fixtures

- `tests/fixtures/mock_cams_cas.pdf` — synthetic CAMS CAS PDF generated by
  `scripts/generate_mock_cams_pdf.py`. Contains 3 folios / 3 schemes with
  synthetic purchase, redemption, IDCW, and adjustment transactions.
- `tests/fixtures/mock_casparser_output.json` — the expected casparser JSON
  output for the mock PDF. Hand-verified golden file.
- `tests/fixtures/xirr_cases.json` — pre-computed (investment, cash flows,
  expected XIRR) tuples from a spreadsheet.

## Market-data provider

All tests use a **stubbed** market-data provider that returns fixture
responses. No real network calls during test runs. The stub is injectable via
the application's dependency-injection seam (a provider interface).

## Financial-maths correctness

XIRR, lot-reduction, and time-weighted return are tested against
**independently computed** answers — not against the implementation under
test. A spreadsheet with the same inputs and outputs serves as the spec.

## Property-based tests

The projection engine and lot-reduction logic are good candidates for
property-based testing (e.g. Hypothesis):

- **Lot reduction:** for any set of lots, reduction FIFO must never create
  negative quantities, and the total redeemed units must equal the sum of the
  consumed lots.
- **Projections:** for any starting balance and deterministic contribution
  schedule, the projected balance must equal the starting balance plus net
  contributions (return is a multiplicative overlay that never changes the
  sign of the balance when contributions are zero).

## CI

Every push runs `mise run check` which executes all four seam layers and
property-based tests. No test is allowed to make a network call.

## Consequences

- The mock PDF must be regenerated when the synthetic data changes. The
  generator script is in the repo — `scripts/generate_mock_cams_pdf.py`.
- Property-based tests are slower than example-based tests, so they are tagged
  and can be run separately (`mise run test-property`).
- The golden JSON fixtures are reviewed and committed alongside the mock PDF.
  Any change to the generator requires regenerating the golden file.
